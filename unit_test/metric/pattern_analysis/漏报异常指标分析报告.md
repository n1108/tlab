## 二、漏报指标的 5 大核心 Pattern

### 🔴 Pattern 1: 错误类指标漏报（最严重）- 45%

**特征指标**:
- `error` (82 次，19.5%)
- `client_error` (62 次，14.8%)
- `error_ratio` (15 次，3.6%)
- `client_error_ratio` (15 次，3.6%)
- `server_error` (14 次，3.3%)

**典型组件**: shippingservice, recommendationservice, cartservice, productcatalogservice

**异常模式**: 
- 错误计数型指标，平时为 0 或接近 0
- 故障时突然上升但幅度不大
- 当前检测方法可能未覆盖离散错误事件

**建议优化**:
```python
# 增加基于错误率阈值的检测
if error_ratio > 5% or error_count > 10:
    trigger_alert()
```

---

### 🟠 Pattern 2: TiDB 专用指标漏报 - 32.4%

**特征指标**:
- `store_size` (28 次，6.7%)
- `memory_usage` (20 次，4.8%)
- `region_pending` (12 次，2.9%)
- `grpc_qps` (11 次，2.6%)
- `leader_count`, `abnormal_region_count` (各 5 次)

**典型组件**: tidb-tikv (90 次), tidb-tidb-0 (31 次), tidb-pd (15 次)

**异常模式**:
- **单调递增型**: store_size 随时间持续增长
- **累积型**: region_pending 逐渐堆积
- **业务相关型**: 与 TiDB 内部机制强相关

**建议优化**:
```python
# 针对 TiDB 指标的特殊检测逻辑
# store_size: 检测增长率突变而非绝对值
# region_pending: 检测队列堆积速度
growth_rate = (current_size - prev_size) / prev_size
if growth_rate > threshold:
    trigger_alert()
```

---

### 🟡 Pattern 3: 流量/QPS 指标漏报 - 13.3%

**特征指标**:
- `response` (15 次)
- `request` (15 次)
- `qps` (15 次)

**典型组件**: 各类微服务

**异常模式**:
- 具有明显的周期性（日周期、周周期）
- 存在长期趋势性（增长或下降）
- 正常波动范围大，难以界定异常

**建议优化**:
- 使用季节性分解 (STL) 分离趋势、周期、残差
- 对残差部分进行异常检测
- 采用 Prophet 等支持季节性的模型

---

### 🟢 Pattern 4: 网络类指标漏报 - 9.5%

**特征指标**:
- `pod_network_receive_bytes` (10 次)
- `pod_network_transmit_bytes` (10 次)
- `pod_network_receive_packets` (10 次)
- `pod_network_transmit_packets` (10 次)

**典型组件**: shippingservice, productcatalogservice, cartservice 等所有微服务

**异常模式**:
- 高波动性（spike 频繁）
- 多 Pod 场景下数据分散（如 productcatalogservice-0/1/2）
- 与业务流量强相关

**数据示例** (从提取的时序看):
```
pod_network_receive_bytes: [152.61, 142.26, 206.48, 170.01, ...]
波动范围：88 - 478，变异系数大
```

**建议优化**:
- 多 Pod 数据聚合（求和或平均）后再检测
- 使用滑动窗口统计（均值 +3σ）
- 结合相关性分析（如网络接收与发送应正相关）

---

### 🔵 Pattern 5: 进程/CPU 资源指标漏报 - 7.1%

**特征指标**:
- `pod_processes` (16 次，3.8%)
- `cpu_usage` (13 次，3.1%)
- `pod_memory_working_set_bytes` (6 次)

**异常模式**:
- **稳定型**: pod_processes 通常保持恒定（如 1, 10）
- **饱和型**: cpu_usage 接近 0 或 1 的边界值
- **缓慢变化型**: 内存使用缓慢增长

**数据示例**:
```
pod_processes: [1.0, 1.0, 1.0, ...]  # 恒定值
pod_cpu_usage: [0.4, 0.4, 0.4, ...]  # 稳定
```

**建议优化**:
- 对稳定指标设置固定阈值（如 processes 变化即异常）
- 对 CPU 使用率检测持续高负载（如>90% 超过 5 分钟）

## 五、根本原因总结

1. **检测方法单一**
   - 过度依赖统计假设（如正态分布）
   - 缺乏对业务指标特性的理解

2. **数据预处理不足**
   - 多 Pod 场景未聚合
   - 缺失值处理不当

3. **缺乏领域知识**
   - TiDB 专用指标需要特殊处理
   - 错误类指标需要阈值 + 趋势结合

4. **评分策略问题**
   - 如果是并集策略仍漏报，说明各基线方法都存在盲区
